# Stage 1 — Membership backend

This is a complete source copy of the uploaded ASP.NET Core backend with the separate membership module integrated and corrected. No frontend is included. Use `TheOne/` as the project root.

**Verification status: source consistency checks completed; NOT compiled or runtime-tested here.** The workspace has no .NET SDK; the SDK download attempt timed out. The PostgreSQL migration, model snapshot and 14 regression tests are supplied for execution on your development machine. Do not treat this package as production-validated.

## 1. Open the source

Extract into a NEW folder, keeping your existing working project as a backup. Open `TheOne/src/TheOne/TheOne.slnx` in your IDE, or use the PowerShell commands below. This package is based on the uploaded backend ZIP, not any later local edits. `CHANGED_FILES.md` identifies changes if you prefer to merge them into your newer checkout.

Do not apply the earlier membership ZIP's manual wiring patches again; they are already integrated here. Original general architecture documents are historical; `PROJECT_DECISIONS.md` and this README govern this stage.

## 2. Configure development

Prerequisites: .NET 10 SDK, PostgreSQL and package access for the versions already used by your source (EF Core 10.0.11). Existing credentials are not included. From `TheOne/`:

```powershell
dotnet tool restore
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Host=localhost;Database=theone_dev;Username=YOUR_USER;Password=YOUR_PASSWORD" --project src/TheOne
dotnet user-secrets set "Jwt:SecretKey" "REPLACE_WITH_A_RANDOM_SECRET_AT_LEAST_32_BYTES" --project src/TheOne
dotnet dev-certs https --trust
```

Use your existing issuer/audience settings and existing SMS/MFA secrets as appropriate. User-secrets apply in Development; production uses environment/secret-store configuration. Do not put live credentials into source files. Membership registration itself sends no SMS.

## 3. Run the regression gate first

Create a separate disposable PostgreSQL database named, for example, `theone_membership_test`. Supply its connection string in your local shell:

```powershell
$env:THEONE_AUTH_TEST_CONNECTION = "Host=localhost;Database=theone_membership_test;Username=YOUR_TEST_USER;Password=YOUR_TEST_PASSWORD"
./scripts/Verify-Membership.ps1
```

This builds the API and test project, then executes the membership tests against real PostgreSQL. Tests apply all migrations to that TEST database and insert synthetic data. They do not send SMS, use real payment services or call translation providers. The migration/model consistency assertion is included. Keep the generated TRX report if assistance is needed.

The delivered migration was authored from the model here, not generated by a running EF CLI. If the model-consistency assertion fails, inspect the reported differences and regenerate the NEW membership migration in a development checkout before using it; do not suppress EF pending-model warnings.

## 4. Review and apply the development migration

Only after the regression gate passes:

```powershell
$env:ASPNETCORE_ENVIRONMENT = "Development"
dotnet ef migrations script 20260910100612_AddAdministrationAndAudit 20260913090000_AddMembershipModule --project src/TheOne.Persistence --startup-project src/TheOne --output membership-migration.sql
# Review membership-migration.sql before updating the development database.
dotnet ef database update --project src/TheOne.Persistence --startup-project src/TheOne
dotnet run --project src/TheOne --launch-profile https
```

The API launch profile uses HTTPS port 7198. In Development, use `/swagger` to exercise the endpoints.

This migration expects the supplied baseline, with NO MembershipApplications, Members or Contributions tables. If the earlier patch was already deployed and membership records exist, do not apply this create-table migration: that database needs a separate additive migration, numbering backfill and resume-credential recovery process. There is deliberately no destructive automatic conversion.

Rolling this migration back drops all three membership tables and their data. Use rollback only on disposable development data; production recovery requires a backup or a forward fix.

## 5. Membership behaviour

- No applicant account or OTP. Start returns a readable reference and a **private 256-bit resume token exactly once**. The database stores only the token's SHA-256 digest.
- Resume, draft save and submission require reference, token and matching contact number. Send credentials in JSON over HTTPS, never query strings. Do not log request/response bodies containing credentials or NID.
- The future frontend should offer copy/save of the credential and use a URL fragment if providing a resume link, keeping it out of server access logs. It must not send tokens to analytics. SMS delivery is not implemented.
- Losing the private token does not fall back to reference + phone. Staff-assisted recovery/rotation is a later management feature; this stage has no recovery endpoint. Staff must not disclose applicant data based only on a phone/reference match.
- Draft saves are partial: omitted/null optional values stay unchanged; empty strings clear text fields. Full-name text can now be corrected before submission. Phone-number change and clearing optional enum/number values are not added in this stage.
- Initial submission fields: Bangla name, English name, phone, Bangla permanent address and Bangla joining purpose; code of conduct must be accepted. This is an explicit provisional minimum, not a finalized business form. `Membership:RequiredSubmissionFields` configures supported additions. Names/phone remain mandatory. NID is optional by default.
- Submitted applications cannot be edited by the applicant. A repeated submit returns 409 and does not create another member.
- `Draft -> Submitted -> Verified -> Approved`. Member becomes Active on approval. Reject is valid only from Submitted or Verified. The legacy application enum value Active is retained for compatibility but is not used by this flow.
- Repeated verification while Verified, approval while Approved, or rejection while Rejected returns current state and preserves the original actor, number and reason. Other invalid transitions return 409.
- All mutations use one PostgreSQL transaction and a per-application advisory lock. Concurrent requests must load state after acquiring the lock. Unique indexes remain database safeguards. Numbering uses two non-resetting sequences; gaps are expected and numbers are not reused after deletion or rollback. Reference year is a display prefix; its sequence does not reset annually.
- Application and member records are committed together at submission. Decision fields and member activation commit together at approval.
- Staff need MFA and the relevant current permission: membership.review, membership.approve or membership.contribute. A SuperAdmin can grant these through existing role administration. This ZIP does not add membership management screens.

## 6. Fees and payments

- Membership approval still requires one recorded MembershipFee payment of at least BDT 100. Donation, monthly-due or event payments never satisfy this condition.
- Payments are manually verified/recorded by staff as bKash or cash. No checkout, gateway, webhooks or automatic confirmation.
- Positive amounts only, at most two decimal places. bKash transaction IDs are trimmed and uppercased, must be alphanumeric, and are unique across all member payments. A duplicate returns 409. Cash records have no transaction ID; repeated cash submissions are NOT automatically deduplicated.
- One external payment currently belongs to one contribution record/category. Splitting a single payment into several categories/periods is not implemented. Do not reuse a transaction ID to simulate allocations.
- Monthly dues/arrears, installment aggregation, receipts, reversals/refunds and non-member donations remain pending. Every payment in this stage still requires an existing member record, including PendingApproval records. The unresolved dues rule is not silently implemented.

## 7. Optional translation

Disabled by default (`Membership:TranslationEnabled=false`). The endpoint now requires the private resume credential and reads only a saved allowlisted field of a Draft. Names cannot be sent through it. It does not save translations automatically.

To enable after separately verifying provider configuration and Bangla support: configure `LibreTranslate:Url`, `GoogleTranslate:ApiKey`, then enable the setting. The field controls the provider tier; callers cannot choose arbitrary translation text or a paid tier flag. IP rate limits are not a spending quota: set provider budget limits before enabling paid suggestions. Provider failure returns 503 without changing the draft.
